# Wake-word and keyword-spotting engines for KIVO (Rust, Windows-first, custom wake words)

Research date: 2026-09-21. Scope: engine comparison, custom-word workflows, licensing, Rust integration, architecture (two-stage + VAD), phrase validation.

## Which engines are viable for KIVO, and how do they compare (custom-word workflow, accuracy, CPU, license, platforms, Rust, maintenance)?

### Takeaway
Picovoice Porcupine is effectively out for a consumer desktop app in 2026: its Free Tier was shut down on 30 June 2026, and commercial use now goes through enterprise sales. The realistic stack is open source. sherpa-onnx KWS (Apache-2.0, official Rust crate, open vocabulary from text, about 3 MB models) is the best fit for "type your own wake word". openWakeWord-style trained models (Apache-2.0 code, trained on synthetic TTS data) give the best accuracy for the fixed default "Hey Kivo", but KIVO must train its own model because the shipped pretrained models are non-commercial.

**openWakeWord**
- License:
  - Code: Apache-2.0.
  - Pretrained models: CC BY-NC-SA 4.0 (non-commercial). — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- Accuracy:
  - The pretrained models target "false-accept rate of <0.5 per hour and a false-reject rate of <5%."
  - The "alexa" model performs competitively against Porcupine. — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- CPU: "A single core of a Raspberry Pi 3 can run 15-20 openWakeWord models simultaneously in real-time." — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- Training:
  - Uses entirely synthetic speech generated by TTS, with several thousand examples minimum.
  - A demo Colab notebook trains a model in under an hour. — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- Built-in extras:
  - Silero VAD, via the `vad_threshold` option.
  - Optional Speex noise suppression (Linux only).
  - "Custom verifier models" trained on a specific user's voice, which filter predictions. — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- Language: the pretrained models are English only. — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- Maintenance:
  - Last release v0.6.0 was on Feb 11, 2024.
  - Recent commits are sparse maintenance work: Python 3.10+ bump and a switch to ai-edge-litert (Oct 2025), and an ONNX-to-TFLite flag (Dec 30, 2025). — [openWakeWord commits](https://github.com/dscripka/openWakeWord/commits/main)
- Home Assistant custom wake-word flow:
  - Type the phrase into a Colab notebook, which generates clips with Piper TTS.
  - You can tweak the phonetic spelling.
  - Training takes "around an hour" (30-60 min) on Colab resources.
  - The flow supports only English. — [Home Assistant: create wake word](https://www.home-assistant.io/voice_control/create_wake_word/)
- openWakeWord runs on the HA server because it is "too large" for ESP32-class devices. — [Home Assistant: about wake word](https://www.home-assistant.io/voice_control/about_wake_word/) (via search summary)

**microWakeWord**
- Design:
  - Aimed at TensorFlow Lite for Microcontrollers (ESP32).
  - Uses streaming MixConv (mixed depthwise convolution) models, adapted from Google Research KWS code.
  - Training uses Piper synthetic samples and SpecAugment, and picks weights to minimize false accepts first. — [microWakeWord repo](https://github.com/kahrendt/microWakeWord)
- Pretrained models are hosted at esphome/micro-wake-word-models. The project is labelled "early release," and training is "intended for advanced users." — [microWakeWord repo](https://github.com/kahrendt/microWakeWord)
- Community wrapper notebooks exist to patch training "gotchas." — [alfiedennen/microwakeword-trainer](https://github.com/alfiedennen/microwakeword-trainer); [ESPHome micro_wake_word](https://esphome.io/components/micro_wake_word/)

**sherpa-onnx keyword spotting (open vocabulary)**
- How it works:
  - KWS is "a tiny ASR system, but it can only decode words/phrases in the given keywords."
  - Keywords are specified as text and need no retraining.
  - Each keyword has a boosting score and a trigger threshold (0-1). For example: `▁HE LL O ▁WORLD :1.5 #0.35`.
  - `sherpa-onnx-cli text2token` converts text to tokens (BPE, CJK, pinyin, phonemes). — [sherpa-onnx KWS docs](https://k2-fsa.github.io/sherpa/onnx/kws/index.html)
- Pretrained KWS models:
  - `sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20` (Chinese and English, about 3 MB)
  - `...-wenetspeech-3.3M-2024-01-01` (Chinese)
  - `...-gigaspeech-3.3M-2024-01-01` (English)
  - The docs give no accuracy metrics. — [sherpa-onnx KWS docs](https://k2-fsa.github.io/sherpa/onnx/kws/index.html)
- License and platforms:
  - Apache-2.0.
  - Runs on Linux, macOS, Windows, Android, iOS and HarmonyOS, on x86/x64/ARM32/ARM64/RISC-V.
  - Bindings: C, C++, Python, JS, Java, C#, Kotlin, Swift, Go, Dart and Rust.
  - Also includes VAD, speaker ID and diarization, ASR and TTS. — [sherpa-onnx repo](https://github.com/k2-fsa/sherpa-onnx)
- Rust:
  - Official safe crate `sherpa-onnx` on crates.io, with a `keyword_spotter.rs` example exposing `KeywordSpotter` / `KeywordSpotterConfig`.
  - The community crate `sherpa-rs` also exists. — [crates.io sherpa-onnx](https://crates.io/crates/sherpa-onnx); [keyword_spotter.rs example](https://github.com/k2-fsa/sherpa-onnx/blob/master/rust-api-examples/examples/keyword_spotter.rs); [thewh1teagle/sherpa-rs](https://github.com/thewh1teagle/sherpa-rs)

**Few-shot / template engines (user records 3-4 samples)**
- local-wake:
  - MIT license.
  - Extracts features with Google's speech-embedding model (ONNX), which openWakeWord also uses, and matches with DTW against 3-4 user reference recordings. No training is needed.
  - Reports 98.6% detection accuracy on clean same-speaker audio (Qualcomm Keyword Speech Dataset). There is no FA/hr figure and no head-to-head benchmark. — [local-wake repo](https://github.com/st-matskevich/local-wake)
  - Recommended on the HA forum for non-English custom words after the Porcupine shutdown. — [HA Community thread](https://community.home-assistant.io/t/porcupine-free-tier-shutdown-alternatives-for-home-assistant-voice-users/1012382)
- EfficientWord-Net:
  - Apache-2.0, few-shot Siamese / ResNet-50 ArcFace embedding, "performs best when 3-4 hotword samples are collected directly from the user."
  - Its README concedes a performance gap versus Porcupine and gives no metrics. — [EfficientWord-Net repo](https://github.com/Ant-Brain/EfficientWord-Net)

**NanoWakeWord**
- A trainable framework configured through YAML. It synthesizes phonetically confusable negative examples and claims to be language-agnostic if audio is provided. — [arcosoph/nanowakeword](https://github.com/arcosoph/nanowakeword)
- A separate project also named NanoWakeWord is a minimal C# port of openWakeWord. — [samartzidis/NanoWakeWord](https://github.com/samartzidis/NanoWakeWord)

**DaVoice**
- Commercial SDK covering wake word, VAD and speaker verification, with Python on Windows, macOS and Linux.
- Custom wake words are produced by DaVoice on request (email info@davoice.io) and delivered as `.onnx`. The free license is for evaluation only. — [DaVoice Python repo](https://github.com/frymanofer/Python_WakeWordDetection); [DaVoice Web repo](https://github.com/frymanofer/Web_WakeWordDetection/)

**Windows' own voice activation**
- The `Windows.ApplicationModel.ConversationalAgent` API with Multiple Voice Assistant (MVA) supports two-stage keyword detection with a hardware or OS software keyword spotter.
- Microsoft says "additional Microsoft configuration may be needed to onboard other voice assistants." The API is aimed at OEM- or Microsoft-onboarded assistants such as Cortana and "Hey Copilot."
- Microsoft recommends that apps add "a more stringent keyword detector" to verify first-pass activations. — [Microsoft Learn: ConversationalAgent](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.conversationalagent?view=winrt-26100); [Microsoft Learn: Voice Activation](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/voice-activation); [MVA](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/voice-activation-mva)

**Other alternatives**
- Outspoken is a hosted service for training and evaluating custom wake-word models (a cloud workflow). — [outspoken.cloud](https://outspoken.cloud/)
- openwakeword.com claims custom wake-word training "in 20+ languages." It appears to be a third-party site, not the dscripka project; unverified. — [openwakeword.com](https://openwakeword.com/)

### Inferences

**Comparison matrix**

| Engine | Custom-word workflow | Rust path | License / commercial | Maintenance |
|---|---|---|---|---|
| sherpa-onnx KWS | Text at runtime, no training | Official crate | Apache-2.0, free | Very active |
| openWakeWord | Full training (synthetic TTS, about 1 h on GPU/Colab) | ONNX via `ort` (melspec, embedding and classifier graphs) | Code Apache-2.0; pretrained models NC, so KIVO must train its own "Hey Kivo" | Low activity |
| microWakeWord | Full training | TFLite, no clean Rust route | Code license not confirmed | Early release |
| local-wake / EfficientWord-Net | Few-shot recordings | Reimplement DTW in Rust over the ONNX embedding | MIT / Apache | Small projects |
| Porcupine | Type-to-train in cloud console | C API | Enterprise-only as of July 2026 | Active |
| DaVoice / Sensory | Vendor-trained | Vendor SDK | Commercial | Active |

**Recommendations**
- **Default engine:** a dedicated trained model for "Hey Kivo" built with the openWakeWord pipeline. Train it with Piper (or other) TTS voices plus real recordings, and run it through `ort`. This gives the lowest false-accept rate for the one phrase most users will keep.
- **Custom and advanced option:** sherpa-onnx KWS for any user-typed phrase, reached through the same Rust crate that can also provide VAD and ASR. An optional second stage can use enrollment-based verification: few-shot embedding plus DTW (local-wake style) or speaker verification.
- The "AI" option could also be to train an openWakeWord model locally in the background from the typed phrase. This is feasible but heavy (see next section).

## How accurate are open-vocabulary text-defined keywords compared with trained models, and do few-shot user recordings help?

### Takeaway
Text-defined open-vocabulary KWS works without training but tends to produce more false alarms on confusable words than a phrase-specific trained model. Research and industry practice both add audio enrollment and/or speaker verification to close the gap. Few-shot recordings (3-4 samples) are the standard enrollment size.

### Cited Findings
- Open-vocabulary user-defined KWS methods "commonly suffer from high false alarm rates with confusable words and are limited to either audio-only or text-only enrollment." PLCL aligns text and audio at the phoneme level so it can use both enrollment modes. — [arXiv:2412.20805](https://arxiv.org/abs/2412.20805)
- Text-enrollment KWS compares acoustic and text embeddings in a shared space. Deep-metric-learning alignment was evaluated on WSJ and LibriPhrase. — [arXiv:2505.16735](https://arxiv.org/abs/2505.16735)
- Research threads that continue into 2026:
  - Prefix bias in open-vocab KWS. — [arXiv:2602.08930](https://arxiv.org/pdf/2602.08930)
  - False-alarm suppression for zero-shot KWS. — [arXiv:2604.03689](https://arxiv.org/pdf/2604.03689)
  - Personalized user-defined KWS combined with text-independent speaker verification. — [arXiv:2606.20106](https://arxiv.org/pdf/2606.20106)
- sherpa-onnx exposes per-keyword boosting score and threshold so each keyword can be tuned for false accepts versus misses, but publishes no accuracy numbers. — [sherpa-onnx KWS docs](https://k2-fsa.github.io/sherpa/onnx/kws/index.html)
- openWakeWord supports custom verifier models trained on a specific user's voice to cut false activations. — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- Few-shot template matching reaches 98.6% on clean same-speaker audio with 3-4 samples. — [local-wake](https://github.com/st-matskevich/local-wake)
- A forum user found openWakeWord custom models unreliable for Japanese, which suggests accuracy varies by language. — [HA Community](https://community.home-assistant.io/t/porcupine-free-tier-shutdown-alternatives-for-home-assistant-voice-users/1012382)

### Inferences
- Best custom-word UX: the user types the phrase, which immediately activates sherpa-onnx KWS. The user then records 3-5 samples.
- Those samples serve three purposes:
  - Tuning the sherpa threshold and boost, by checking the recordings trigger at the chosen threshold.
  - Building a DTW or embedding template, or a speaker-verifier, used as a second stage.
  - Optionally seeding a background openWakeWord training run.

### Gaps
- No published side-by-side FA/hr for sherpa-onnx text KWS versus an openWakeWord model trained for the same phrase. KIVO should run its own measurement, for example on hours of podcast or LibriSpeech audio.

## Is on-device training of a custom model practical inside a desktop app?

### Takeaway
It is possible but heavy. The openWakeWord / microWakeWord recipe needs thousands of TTS clips plus large negative and background datasets, and takes about an hour even on Colab GPUs. On a consumer CPU it would take considerably longer. It suits an optional "enhance my wake word" background job, not the core "add a wake word" flow.

### Cited Findings
- openWakeWord training uses thousands of synthetic TTS examples. The demo notebook trains in under an hour (Colab). — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- Home Assistant's flow takes 30-60 min on Colab, "around an hour," and is designed for "small-scale, non-commercial personal use." — [Home Assistant: create wake word](https://www.home-assistant.io/voice_control/create_wake_word/)
- microWakeWord generates synthetic samples with Piper, applies SpecAugment, and is "intended for advanced users." — [microWakeWord](https://github.com/kahrendt/microWakeWord)
- NanoWakeWord synthesizes phonetically confusable negatives automatically. — [nanowakeword](https://github.com/arcosoph/nanowakeword)

### Inferences
- A practical on-device design:
  - Local Piper or sherpa-onnx TTS (sherpa-onnx ships TTS) generates a few thousand positive clips across voices and speeds.
  - Augment with noise and room impulse responses.
  - Freeze the shared embedding model and train only openWakeWord's small classifier head. This is the cheap part.
  - Negatives come from a bundled precomputed feature set, so large corpora need not be downloaded.
  - This could fit in tens of minutes on a CPU, but that is an estimate and must be benchmarked.
- The training stack is Python/PyTorch. Shipping it inside a Rust app would mean bundling a Python runtime or porting the head training, for example with `candle` or `burn`, or ONNX Runtime training.

### Gaps
- No sourced CPU-only training time for openWakeWord or microWakeWord.

## Is two-stage detection (tiny detector plus verifier) a best practice, and how does VAD gating fit in?

### Takeaway
Yes. Apple, Microsoft and openWakeWord all use a cheap first pass followed by a stricter second pass, and VAD gating in front further cuts CPU when there is no speech.

### Cited Findings
- Apple "Hey Siri" uses two passes:
  - A small DNN (5 layers x 32 units) runs on the Always-On Processor.
  - Above threshold it wakes the main CPU, which runs a larger DNN (5 x 192).
  - This uses about 5% of the compute budget. — [Apple ML Research: Hey Siri](https://machinelearning.apple.com/research/hey-siri)
- Apple also personalizes with speaker vectors. — [Apple: Personalized Hey Siri](https://machinelearning.apple.com/research/personalized-hey-siri)
- Apple published on progressive detection that trades accuracy against latency. — [arXiv:2010.15446](https://arxiv.org/pdf/2010.15446)
- Microsoft says platform first-pass detectors "can result in too many unintended activations" and recommends "a more stringent keyword detector" in the app. — [Microsoft Learn: ConversationalAgent](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.conversationalagent?view=winrt-26100)
- openWakeWord includes Silero VAD gating (`vad_threshold`) and optional per-user verifier models. — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- sherpa-onnx bundles VAD and speaker identification in the same library as KWS. — [sherpa-onnx repo](https://github.com/k2-fsa/sherpa-onnx)

### Inferences
Suggested KIVO pipeline:
1. Capture mic audio at 16 kHz mono in 10-30 ms frames.
2. An energy gate, then Silero VAD (via sherpa-onnx or `ort`), runs only when energy is above the noise floor.
3. Stage 1 runs only while VAD reports speech, with a small ring buffer of pre-roll: either the "Hey Kivo" openWakeWord model or sherpa-onnx KWS for custom words.
4. Stage 2 runs on a hit, over the buffered 1.5-2 s. Options:
   - a stricter model, such as sherpa KWS confirming the openWakeWord hit, or the reverse;
   - enrollment template match;
   - optional speaker verification.
5. Wake.

Detector output can also be cross-checked by the streaming ASR's first words, which gives a free third check.

### Gaps
- No measured desktop CPU savings from VAD gating were found.

## What guidance should the app use to validate user-chosen wake words?

### Takeaway
Validate for 2-4 syllables (at least 3 is safer), six or more phonemes, varied vowels, and no common words, names or everyday phrases. Then run an automated confusability check.

### Cited Findings
- Picovoice advises 2-4 syllables and distinctive phonemes. The best phrases are "six or more phonemes long," phonetically distinct from common speech, with a mix of vowel sounds. Avoid names, common commands and conversational phrases. Very long phrases hurt UX. — [Picovoice: Tips for choosing a wake word](https://picovoice.ai/docs/tips/choosing-a-wake-word/)
- Home Assistant recommends "a word or short phrase (3-4 syllables) that is not commonly used," and adjusting phonetic spelling until the TTS pronunciation matches. — [Home Assistant: create wake word](https://www.home-assistant.io/voice_control/create_wake_word/)

### Inferences
Suggested validator:
1. Convert the phrase to phonemes with a G2P model; sherpa-onnx `text2token` / phoneme lexicons or espeak-ng are options.
2. Score it on:
   - syllables (reject 1, warn at 2, prefer 3-4);
   - phoneme count (at least 6);
   - distinct vowel count;
   - edit distance to a list of frequent English words, bigrams and common names;
   - collision with other enabled wake words and with KIVO commands.
3. Play the phrase back with TTS so the user can confirm the pronunciation.
4. Have the user record 3-5 samples. Check they trigger at the chosen threshold.
5. Run a short false-alarm test on a bundled clip of background speech. Report the result as "good / fair / risky."

"Hey Kivo" has 3 syllables and roughly 6 phonemes (/h eɪ k iː v oʊ/). It fits the guidance, but the "Kivo" part is short, so "Hey" contributes much of the length.

### Gaps
- No quantitative study found that links syllable count to FA/hr.
