# Build KIVO as a pill that grows

KIVO should be a **resident tray app with two surfaces**: a full main window (Control Center) for conversation history, settings and onboarding, and a small **non-activating, always-on-top voice pill at the bottom center of the active monitor**. The pill appears on "Hey Kivo" or a hotkey, plays a start chime, and grows upward into a transcript card when there is text to show. This is the pattern Windows users already know from Copilot Voice, Wispr Flow, Superwhisper and Win+H. The Siri- and Gemini-style screen-edge glow is a phone pattern: on a desktop it holds no text, is ambiguous across several monitors, and costs the most GPU. It should be at most an optional 400 ms accent. Because a wake word needs a process that keeps running, closing the window should hide KIVO to the tray by default. Microsoft's own Copilot app ships exactly this behavior, and exactly this setting ("On close, keep the app running"). Wake word and launch-at-login should both be opt-in. Every time the microphone opens or closes, KIVO should play a short sound together with a visual state change, and each cue should have its own toggle. The design is **feasible in Tauri v2 on Windows**, since every piece has a first-party API or plugin. The risks are concentrated in the overlay: a white flash when a hidden transparent window is shown, focus stealing, whole-window-only click-through, idle GPU drain, and exclusive-fullscreen games, which will cover the pill. Each has a known workaround, and none blocks the design. For the build, use shadcn/ui and Tailwind v4 as the design system, adapt ElevenLabs' and LiveKit's MIT/Apache voice visualizers, and custom-build only the overlay shell, the state machine and the audio bridge.

## A wake word forces KIVO to keep running after the window closes

A wake word requires a resident process. Microsoft states that "Hey, Copilot" works only while the Copilot app is "open, minimized, or running in the background", and that it uses an on-device spotter with a **10-second in-memory audio buffer that is never stored**. Audio goes to the cloud only after the wake word is detected ([Windows Insider Blog](https://blogs.windows.com/windows-insider/2025/05/14/copilot-on-windows-hey-copilot-begins-rolling-out-to-windows-insiders/)). Copilot now exposes this as two explicit settings: "Auto start on login", which starts the app in the background with a tray icon ([ElevenForum](https://www.elevenforum.com/t/enable-or-disable-auto-start-copilot-on-login-in-windows-11.19626/)), and **"On close, keep the app running"**. With the second setting on, closing leaves a tray icon to reopen or quit from. With it off, closing quits ([ElevenForum](https://www.elevenforum.com/t/enable-or-disable-keep-copilot-app-running-on-close-in-windows-11.45683/)). Teams offers the same toggle, and Discord offers a close-to-tray option ([Microsoft Q&A](https://learn.microsoft.com/en-sg/answers/questions/7312/cant-close-teams-window)).

The counter-argument deserves a hearing. Microsoft's older, still-published notification-area guide says minimizing to the tray "is no longer recommended". Where an app does offer it, the guide says it should be opt-in and tied to Minimize, not Close ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/uxguide/winenv-notification)). Users complain that "Almost universally X is expected to close an application" ([Discord feedback](https://support.discord.com/hc/en-us/community/posts/360029987811-Add-an-option-to-fully-close-Discord-on-x)). The press also greeted Copilot's autostart as "the option nobody was crying out for" ([TechRadar](https://www.techradar.com/computing/windows/windows-11-is-set-to-offer-the-option-nobody-was-crying-out-for-having-copilot-automatically-load-in-the-background-when-the-pc-boots)). The resolution is to separate the two concerns. **Close-to-tray defaults on**, because the core feature needs it, but KIVO must say so clearly: during onboarding, and with a one-time toast the first time the window is closed. Close must behave the same way for X, Alt+F4 and the taskbar's "Close window". Discord users specifically complain that Alt+F4 exits while X hides ([Discord](https://support.discord.com/hc/en-us/community/posts/360040720652-Also-close-to-tray-when-Alt-F4-is-pressed-and-the-relevant-setting-is-enabled)). **Launch at login and the wake word default off.** Both "Hey Copilot" and Voice Access autostart ship opt-in ([Microsoft Support](https://support.microsoft.com/en-us/accessibility/windows/voice-access/set-up-voice-access)), and Microsoft's guidance is "Don't turn everything on by default and expect users to turn features off" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/uxguide/winenv-notification)).

The way KIVO was launched should decide what the user sees. Wispr Flow starts hidden in the tray when it is launched at login, and opens its main window when launched manually ([Wispr Flow Help](https://docs.wisprflow.ai/articles/7492559320-quit-and-relaunch-wispr-flow)). KIVO should register autostart with a `--autostart` flag and start with no window in that case. Any manual launch should show the main window. The tray alone cannot tell users that KIVO is still running. Windows 11 hides most tray icons behind the overflow chevron, apps cannot promote themselves out of it, and Windows sometimes re-hides icons after an update changes the exe path ([Microsoft Tech Community](https://techcommunity.microsoft.com/discussions/windowsinsiderprogram/windows-11-occasionally-resets-some-tray-icons-to-be-hidden/3887241)). The hotkey, the wake word and the first-close toast have to do that job. A notification also temporarily promotes a hidden icon ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/uxguide/winenv-notification)).

The main failure mode of the two-surface model is already on record. In Claude Desktop, relaunching after close produced only a silent tray icon and a broken quick-entry bar, and the user had to kill the process ([anthropics/claude-code #39336](https://github.com/anthropics/claude-code/issues/39336)). Users also filed requests for the taskbar icon to open the full app instead of the quick bar ([#22420](https://github.com/anthropics/claude-code/issues/22420)). KIVO's rule should therefore be absolute: **a relaunch, or a left-click on the tray icon, always shows and focuses the main window**, never the pill. The tray's right-click menu should follow Microsoft's order. "Open KIVO" comes first, in bold, followed by Pause/Resume listening. Microsoft says "All background tasks must have a Suspend/Resume command", and for KIVO that command doubles as a privacy control. Then come Settings and Quit. Mic-muted, paused and error states should appear as small overlays on the icon, not as animations ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/uxguide/winenv-notification)).

## On a desktop the pill beats the glow, and it needs a card

The industry has settled on three visual families. The first is an **edge glow**: Apple's Siri is "an elegant glowing light that wraps around the edge of the screen" on iPhone and iPad, and Gemini is testing a similar glow around the screen perimeter. The second is a **pill**: the Gemini overlay "starts as a circle that quickly expands … into a wide pill" ([9to5Google](https://9to5google.com/2025/08/25/gemini-overlay-pill/)), Wispr Flow has its Flow Bar, and Copilot Voice has its floating UI. The third is a **docked bar or panel** with text, such as Voice Access and Win+H. The glow lives on phones. On Mac, Apple instead lets "users … place Siri anywhere on their desktop" ([Apple Newsroom](https://www.apple.com/newsroom/2024/06/introducing-apple-intelligence-for-iphone-ipad-and-mac/)). In iOS 27, even the iPhone moved away from the rainbow edge toward an orb that expands out of the Dynamic Island ([MacRumors](https://www.macrumors.com/2026/06/16/iphone-18-could-make-siri-a-circle/)). None of Microsoft's desktop voice surfaces uses a glow. **Copilot's floating UI sits at the bottom of the screen**, the Voice Access bar is docked at the top, and Win+H is a small floating panel ([Windows Insider Blog](https://blogs.windows.com/windows-insider/2025/05/14/copilot-on-windows-hey-copilot-begins-rolling-out-to-windows-insiders/); [Microsoft Support](https://support.microsoft.com/en-US/accessibility/windows/voice-access/get-started-with-voice-access)).

Text is the deciding factor. In NN/g's usability testing, a participant repeated herself because she "didn't see transcription on screen" and assumed Siri had not heard her. Users liked a spoken answer paired with on-screen confirmation, and were overloaded by long spoken answers that could not be replayed ([NN/g](https://www.nngroup.com/articles/intelligent-assistant-usability/)). A glow cannot show "what I heard". A pill is too small to hold an answer. A corner card holds text but covers content and collides with Windows toasts in the bottom-right. The combination that works is the **pill that expands into a card**. The field is converging on it: Gemini's circle becomes a pill, Siri's orb becomes a prompt, and ChatGPT in November 2025 moved voice into the chat so that replies stream as live text ([MacRumors](https://www.macrumors.com/2025/11/26/chatgpt-voice-mode-update-seamless-chat/)). An open-source spec modeled on Wispr describes the same tiers: glance at a 64x32 pill, talk, then summon a 560x640 panel that grows upward from the pill. The same spec lists "no focus steal" and Esc-to-cancel as core requirements ([elizaOS #20483](https://github.com/elizaOS/eliza/issues/20483)).

That settles the three invocation options in the brief. The glow is the wrong primary surface. The animated pill is the right anchor. The transcript widget with a way to chat directly is the right expanded state, and it should grow out of the pill rather than sit in a fixed corner. A whole third-party utility exists only to move Wispr's fixed bottom-center pill ([PillFloat](https://github.com/OrangeAKA/pillfloat)), so KIVO's pill should be draggable and remember its position for each monitor. The glow can survive as an optional personality accent: a thin 2–4 px gradient on the active monitor for about 400 ms at wake, which then hands off to the pill. It should switch off automatically under reduced motion, because WCAG 2.3.3 requires that motion triggered by an interaction can be disabled ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)), and under Focus/Do Not Disturb or fullscreen. No controlled study compares glow, pill and card on a desktop, so the choice rests on product precedent and accessibility guidance. It should be checked with quick user tests on multi-monitor and gaming setups.

States should be carried by color, motion and sound together, never by color alone. Alexa's ring shows the pattern: a cyan spot on blue means listening, and spinning blue means processing ([How-To Geek](https://www.howtogeek.com/what-do-alexas-light-colors-mean/)). In the Wispr-style spec, "red + animated bars = mic is hot", and a flat waveform honestly signals a dead mic ([elizaOS #20483](https://github.com/elizaOS/eliza/issues/20483)). Sessions end the way Copilot's do: the X button, a few seconds of silence with a hang-up chime, or saying "Goodbye" ([Microsoft Support](https://support.microsoft.com/en-us/microsoft-copilot/copilot-wake-word-hey-copilot)). Passive wake-word listening should show nothing at all, so that the visual "mic is hot" state keeps its meaning.

## Every mic open and close gets a sound, and every sound can be switched off

Amazon has published the clearest rules. Alexa plays a Start of Request sound "immediately after the wake word is detected" and an End of Request sound "at the end of speech input". The end sound tells the user they were heard "without looking at the screen". Both sounds must fire together with the visual Listening state, and must repeat each time the mic opens or closes during a multi-turn session. Amazon also requires: "Allow customers to turn off the Start and End of Request sounds" ([Alexa Auto](https://developer.amazon.com/en-US/docs/alexa/alexa-auto/invoking-alexa.html)). Copilot plays a chime on wake and another on hang-up ([Windows Insider Blog](https://blogs.windows.com/windows-insider/2025/05/14/copilot-on-windows-hey-copilot-begins-rolling-out-to-windows-insiders/)). The defaults vary. On Echo speakers the sounds are off by default ([Amazon](https://www.amazon.com/b?ie=UTF8&node=21341310011)). Wispr has a separate "Interaction Sounds" switch ([Wispr Flow Help](https://docs.wisprflow.ai/articles/9454889914-how-to-disable-wispr-flow-notifications-on-ios)). Phones have been dropping activation chimes because the screen already shows the state. KIVO's pill may be off-screen, hidden in fullscreen, or disabled, so **KIVO should play sounds by default** and make every one of them switchable.

The sound set should stay small. Google's guidance is to use "just a few sounds that are easily distinguishable", and "If you feel like you have to teach users what an earcon means, don't use an earcon" ([Google Conversation Design](https://conversation-design.web.app/conversational-components/earcons/)). A 2023 meta-analysis supports this: abstract earcons were recognized less accurately and more slowly than auditory icons or speech ([Auditory Perception & Cognition](https://www.tandfonline.com/doi/abs/10.1080/25742442.2023.2219201)). Four cues are enough: listen-start, listen-stop, error/cancel, and an optional task-done confirmation. A "thinking" loop, if KIVO adds one, should be off by default and start only after about a second of silence. That last point is design judgment, since no source documents a thinking earcon. Brewster's earcon guidelines give concrete numbers. Notes should last at least **0.0825 s**, fundamentals should sit between about **150 Hz and 5 kHz**, playback should be **10–20 dB above background**, and sequential earcons need a gap of about 0.1 s. Rhythm and note count, not absolute pitch, are what make cues distinguishable ([Brewster](https://www.dcs.gla.ac.uk/~stephen/earcon_guidelines.shtml)). In practice that means a rising two-note start, a single resolving stop note, and a low descending two-note error, each under about 300 ms. Amazon built its Echo sounds from a three-note "A-ma-zon" motif. The wake sound was modeled on a human "uh-huh", and **users can talk over it** ([Engadget](https://www.engadget.com/amazon-echo-sounds-explained-160055039.html)). KIVO needs its own motif. Alexa's terms restrict its sounds to Alexa features, and CC0 packs such as Kenney's UI Audio are good placeholders ([Kenney](https://kenney.nl/assets/ui-audio)).

The pipeline detail matters as much as the sound itself. Windows' voice-activation design keeps a burst buffer holding **250 ms before the keyword** and keeps capturing after detection so that "no data after the keyword is lost". It supports both staged commands ("Hey Cortana … wait for the earcon … command") and chained ones, where the command follows the keyword directly ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/voice-activation)). KIVO must therefore never pause capture to play the start chime, and must keep the chime out of speech recognition. On Windows 11, the AEC reference can be pointed at the render endpoint KIVO plays through with `SetEchoCancellationRenderEndpoint` ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iacousticechocancellationcontrol-setechocancellationrenderendpoint)). KIVO should also timestamp the chime window and gate voice-activity detection during it, to cover setups with weak AEC such as speakers with a laptop mic. It should suppress or raise the wake-word threshold while its own TTS plays. Amazon's patent literature treats a wake word heard during device-only playback as probable echo ([USPTO 10586534](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10586534)). One open-source spec targets activation feedback within **150 ms** of wake ([jerryfane/voice #2](https://github.com/jerryfane/voice/issues/2)). No vendor publishes an official figure, but pre-decoded sounds on a low-latency stream make that target achievable.

## Settings must let the overlay disappear without silencing the assistant

Users need a way to turn off the visual conversational component while keeping voice. Precedents exist. Wispr lets users hide the Flow Bar "for 1 hour" or turn it off entirely under Settings > System ([Wispr Flow Help](https://docs.wisprflow.ai/articles/5002934560-why-is-the-wispr-bar-is-not-appearing-or-disappearing)). ChatGPT kept its old full-screen orb as an opt-in "Separate mode" after moving voice inline ([OpenAI Voice FAQ](https://help.openai.com/en/articles/8400625-voice-mode-faq)). Copilot lets users choose what Alt+Space opens: Full Window, Quick View or None ([ElevenForum](https://www.elevenforum.com/t/change-how-copilot-opens-with-alt-spacebar-shortcut-in-windows-11.34184/)). KIVO should offer an **Overlay style** control with four values: Pill + card (default), Pill only, Card only, and Off. With Off, KIVO relies on sounds, the tray icon state and spoken replies. Around that control it needs a "Hide overlay for 1 hour" tray action, an optional wake-glow toggle, and a motion toggle that follows Windows "Animation effects" by default. Automatic audio-only fallback in fullscreen and Focus should also be configurable. Sounds should never be the only channel, and visuals should never be the only channel either. Apple's guidance is to combine color, text and sound so feedback survives "whether they silence their device, look away from the screen, or use VoiceOver" ([Apple HIG](https://developers.apple.com/design/human-interface-guidelines/patterns/feedback/)). Two rules follow: disabling both the overlay and all sounds should trigger a warning, and state changes should also go out as UI Automation announcements for screen-reader users.

## Borrow the voice visuals, build the overlay shell

React owns the voice-UI ecosystem, and the two best sources are copy-paste registries rather than dependencies. **ElevenLabs UI** (MIT, about 2.4k stars, active) is "a component library built on top of shadcn/ui". It ships `orb`, `bar-visualizer`, `live-waveform`, `transcript-viewer`, `conversation`, `message`, `mic-selector` and `shimmering-text` ([elevenlabs/ui](https://github.com/elevenlabs/ui)). Its components are provider-agnostic. The orb takes `getInputVolume()`/`getOutputVolume()` functions ([orb.tsx](https://raw.githubusercontent.com/elevenlabs/ui/main/apps/www/registry/elevenlabs-ui/ui/orb.tsx)). The bar visualizer already animates `listening`, `thinking` and `speaking` states ([bar-visualizer.tsx](https://raw.githubusercontent.com/elevenlabs/ui/main/apps/www/registry/elevenlabs-ui/ui/bar-visualizer.tsx)). LiveWaveform is plain Canvas 2D ([live-waveform.tsx](https://raw.githubusercontent.com/elevenlabs/ui/main/apps/www/registry/elevenlabs-ui/ui/live-waveform.tsx)). All of them can be fed from KIVO's Rust audio levels over Tauri events. **LiveKit Agents UI** (Apache-2.0) provides bar, radial, wave and "aura" visualizers for React 19 and Tailwind 4 ([LiveKit Agents UI](https://github.com/livekit/components-js/tree/main/packages/shadcn)). Its aura is a self-contained raw-WebGL shader, but it imports `livekit-client` track types that KIVO would have to strip out ([aura source](https://github.com/livekit/components-js/blob/main/packages/shadcn/components/agents-ui/agent-audio-visualizer-aura.tsx)). Pipecat's kit and orb-ui pull in transport SDKs KIVO does not need ([voice-ui-kit](https://github.com/pipecat-ai/voice-ui-kit)). siriwave was last pushed in 2024 ([kopiro/siriwave](https://github.com/kopiro/siriwave)).

The clean, minimal macOS-like look comes from tokens, not from a "macOS kit". react-desktop is dead, last pushed in 2023 ([react-desktop](https://github.com/gabrielbull/react-desktop)), and Puppertino is useful only as visual reference ([Puppertino](https://github.com/codedgar/Puppertino)). The base should be **shadcn/ui on Base UI**, which has been the default for new shadcn projects since July 2026 ([shadcn changelog](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)), with Tailwind v4 and **Inter or Geist** (both OFL-1.1). The KIVO look comes from custom tokens: 12–16 px radii, soft CSS shadows, and translucency. **SF Pro cannot legally ship in a Windows app** ([Apple Fonts](https://developer.apple.com/fonts/)). Aceternity Pro code bans redistribution of its source ([Aceternity licence](https://ui.aceternity.com/licence)). Motion (MIT) handles state transitions, and its `LazyMotion` + `m` entry is 4.6 kb initial ([motion.dev](https://motion.dev/docs/react-reduce-bundle-size)). Rive (MIT) is the premium option if a designer authors the orb, because its data-binding view models can take a live mic-level number ([Rive blog](https://rive.app/blog/data-binding-in-rive-a-shared-language-for-designers-and-developers)).

The one thing no library solves is idle cost, and that is why the overlay shell must be custom. One Tauri app kept an NVIDIA dGPU at **P0 (about 13 W) instead of P8 (about 3.8 W)** while visually idle ([tablo #79](https://github.com/unravel-team/tablo/issues/79)). Chromium only throttles animation once the WebView2 controller's `IsVisible` is false, and Tauri's `hide()` does not set it. The fix is to pair window visibility with WebView visibility at every show and hide call ([tablo PR #80](https://github.com/unravel-team/tablo/pull/80)). ElevenLabs' orb uses three.js and react-three-fiber's `useFrame`, which renders every frame while mounted. That makes it unsuitable for an always-available overlay unless it is ported to raw WebGL. The pill should render **zero frames at rest**: static CSS when idle, and a Canvas or shader loop only while listening or speaking.

## Tauri v2 can do all of it, and the traps are in the overlay

Every lifecycle piece is first-party. The tray comes from the `tray-icon` feature, and `show_menu_on_left_click(false)` separates the left-click action from the menu ([Tauri tray guide](https://v2.tauri.app/learn/system-tray/)). Close-to-tray is `CloseRequested` → `hide()` + `prevent_close()` ([discussion #2684](https://github.com/tauri-apps/tauri/discussions/2684)). The single-instance plugin passes the second launch's arguments to the running app and "must be the first one to be registered" ([Tauri single-instance](https://v2.tauri.app/plugin/single-instance/)). Autostart writes the HKCU Run key and accepts launch arguments ([Tauri autostart](https://v2.tauri.app/plugin/autostart/)). The global-shortcut plugin reports both `Pressed` and `Released`, so push-to-talk works ([Tauri global-shortcut](https://v2.tauri.app/plugin/global-shortcut/)). The overlay window gets `transparent`, `decorations: false`, `alwaysOnTop`, `skipTaskbar`, `visible: false` and, from **Tauri 2.11, `focusable: false`**. With `focusable: false`, tao re-applies `WS_EX_NOACTIVATE` every time it rebuilds the window's styles, so the pill never steals the user's keyboard focus ([codenotch PR #199](https://github.com/vinzdg/codenotch/pull/199); [docs.rs tauri](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewWindow.html)).

The pitfalls are specific and known:

| Pitfall | Evidence | Mitigation |
|---|---|---|
| White flash when a hidden transparent window is shown | Open as of Tauri 2.8.5 ([tauri#14515](https://github.com/tauri-apps/tauri/issues/14515)) | Create the overlay hidden at startup. Set `WEBVIEW2_DEFAULT_BACKGROUND_COLOR=0` before the Builder; Microsoft says the env var avoids the API's flicker ([WebView2 spec](https://github.com/MicrosoftEdge/WebView2Feedback/blob/main/specs/BackgroundColor.md)). Call `show()` only after the frontend reports it has painted, then animate opacity. Needs a spike. |
| White 1px border and rounded corners | `set_shadow(true)` adds them on undecorated Windows 11 windows ([docs.rs](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewWindow.html)) | `shadow: false`, and draw the shadow in CSS inside a slightly larger window |
| Focus stealing | `focus: false` unreliable ([tauri#11566](https://github.com/tauri-apps/tauri/issues/11566)); manual `WS_EX_NOACTIVATE` is lost when click-through is toggled ([codenotch #199](https://github.com/vinzdg/codenotch/pull/199)) | `focusable: false` (Tauri ≥ 2.11). Enable focus temporarily only while the user types in the card. |
| Click-through is all-or-nothing | No per-region hit-testing ([tauri#2090](https://github.com/tauri-apps/tauri/issues/2090)); hover cannot turn it back off ([deskpet PR #3](https://github.com/Scyyyy4/deskpet/pull/3)) | Size the window exactly to the pill or card. If needed, poll the cursor in Rust at 30–60 Hz and toggle on transitions. |
| Global-shortcut deadlock | The handler holds a mutex; registering shortcuts or creating a webview inside it deadlocks ([plugins-workspace#3590](https://github.com/tauri-apps/plugins-workspace/issues/3590)) | The handler only sends a message on a channel; the real work is deferred |
| Hotkey limits | RegisterHotKey-style chords only, so no bare modifier or mouse button ([Tauri global-shortcut](https://v2.tauri.app/plugin/global-shortcut/)); Alt+Space is claimed by Copilot, ChatGPT, Raycast and Flow Launcher ([Raycast](https://manual.raycast.com/settings)) | Choose a less contested default, detect registration failure, and prompt the user to rebind |
| Autostart entry vanishes | The Run key is removed after one boot, still open ([plugins-workspace#771](https://github.com/tauri-apps/plugins-workspace/issues/771)) | On each launch, compare `is_enabled()` with the user's preference and re-enable if needed |
| Relaunch fails to show a hidden window | `set_focus()` fails on a hidden window ([tauri#12936](https://github.com/tauri-apps/tauri/issues/12936)) | Call `show()` → `unminimize()` → `set_focus()` on the main window |
| App exits when the last window closes | `ExitRequested` needs `prevent_exit()`, but only when `code` is `None` ([discussion #11489](https://github.com/tauri-apps/tauri/discussions/11489)) | Tell a deliberate quit apart from the last window closing |
| Exclusive-fullscreen games, Start menu, UAC | Exclusive fullscreen bypasses DWM ([Staged](https://staged.gg/blog/always-on-top-over-fullscreen-game)); Start and UAC sit in higher z-bands that require UIAccess and signing ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-securityoverview)) | Accept it. Detect fullscreen and fall back to audio cues plus the tray state. |
| Acrylic lag | Bad drag and resize performance on Win10 1903+ and Win11, broken on 22H2 ([window-vibrancy#47](https://github.com/tauri-apps/window-vibrancy/issues/47), [#45](https://github.com/tauri-apps/window-vibrancy/issues/45)) | Use acrylic only on a fixed-size pill, with a solid CSS fallback. Mica samples the wallpaper, so it looks flat over other apps. |
| Cold start of the WebView | Microsoft names WebView2 cold start as the main bottleneck and advises reuse over re-creation ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)) | Preload the overlay hidden at startup and keep it as a lightweight separate entry |

A full-screen transparent WebView2 window for the edge glow is possible. It is the weakest part of the design because it keeps a monitor-sized GPU surface alive and needs one window per monitor, and nobody has published measurements of its cost. If KIVO ships the glow, it should start as four thin edge strips per monitor and fall back to a native windows-rs/DirectComposition or wgpu window driven straight from the Rust audio levels if power measurements are poor ([ZeroIn-Crosshair](https://github.com/mrdhnto/ZeroIn-Crosshair) shows a working Rust click-through overlay). KIVO has a separate Rust runtime, so single-instance must also be enforced there, with a named mutex or IPC pipe, so that two wake-word listeners never share one mic. Per-window memory, show latency and idle GPU draw have no published Tauri figures and belong in the first prototype.

## Recommended design

**Lifecycle**

| Event | Behavior |
|---|---|
| First launch | Main window opens with onboarding: welcome → mic permission and test → confirm hotkey (with conflict check) → opt-in wake word (explain on-device spotting) → opt-in "Start KIVO when I sign in" → explain close behavior → try it once |
| Manual launch (while not running) | Main window shown |
| Launch at login (opt-in, `--autostart`) | No window. Tray icon; hotkey and wake word active |
| Relaunch while running | Single-instance forwards the launch; main window is shown, unminimized and focused |

## Conclusion

The research reframes the question. The brief asked which visual KIVO should use, but the harder problem is trust in a process that is always listening. Glow, pill and card are really three answers to three separate trust needs. The glow says "I woke up". The pill with its paired chimes says "the mic is hot right now". The card says "this is what I heard, and this is what I'll do". A desktop companion needs the second and third every time, and the first only as flavor. That is why the pill that grows into a card, backed by sounds on every mic transition, beats the more cinematic glow.

The engineering risk has moved as well. Tauri covers the lifecycle completely. The remaining uncertainty is in three unmeasured numbers: whether the hidden-to-shown flash is really gone, how many watts an idle or animating overlay draws on a dGPU laptop, and how long it takes from hotkey to first frame. A one-week spike that measures those three things, with the overlay recipe above and PresentMon running, will settle more of KIVO's design than any further desk research.
